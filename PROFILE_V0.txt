PROFILE_V0: HOW THE TEST INPUTS ARE WRITTEN (O4M Record Tests 2026 v1.0, tests T3 and T14a, vector profile v0)
Draft, 14 November 2026. Format only. This sheet tells you how an input file is written. It does not tell you what verdict an input deserves; that is for you to decide from the specification, and to record in CHOICES.txt. It holds no expected results. Every item is a "vector profile v0" choice, not a standard.

1. Files
One input is one JSON file, UTF-8, with no byte order mark. Nesting is at most 16 levels. A T3 file has the top-level keys declaration and records. A T14a file has the top-level keys declaration and checkpoints. The file name ends with __T3.json or __T14a.json.

2. Allowed value types
Keys are ASCII names. Values are strings, integers, booleans, lists and objects. There are no nulls and no floats. An integer is a whole number between minus (2 to the power 53, minus 1) and plus (2 to the power 53, minus 1). Counters and seq are not negative. Strings are Unicode NFC. A boolean is not an integer.

3. Field table (29 names)
declaration (object): consequential_action_types (list of strings), tolerances (object: max_gap integer, max_clock_skew_s integer, max_unsealed_window_s integer), fail_mode (string, "fail-closed" or "fail-open"), monitors (list of strings), declared_gaps (list of objects).
declared_gaps entry (object): stream_id (string), from_seq (integer), to_seq (integer), action_type (string), reason (string).
records (list, T3 only), each record (object): stream_id (string), seq (integer), prev_hash (string), type (string, "event" or "teardown"), data (string), hash (string), and for a teardown also last_seq (integer).
checkpoints (list, T14a only), each checkpoint (object): checkpoint_id (string), received (integer), accepted (integer), dropped (integer), policy (string, "fail-closed" or "fail-open"), and optionally provenance (string, "SOURCE-LOCAL", "INDEPENDENTLY-RECONCILED" or "UNVERIFIED"; if absent, SOURCE-LOCAL).
Counters mean: received is what the capture point received; accepted is what it passed on; dropped is what it did not pass on.

4. The chain (T3)
Each stream is a separate chain, named by stream_id. seq starts at 1 and goes up by 1.
The first record of a stream has prev_hash equal to 64 zero characters. Every later record has prev_hash equal to the hash of the previous record in the same stream.
hash is the SHA-256 of the record's canonical bytes, with the record's own "hash" field left out, written as 64 lowercase hexadecimal characters. Canonical bytes: the record as JSON with keys sorted, no spaces (separators "," and ":"), characters not escaped, encoded as UTF-8. For this restricted subset that equals RFC 8785 (JCS).
Teardown: a stream may end with one record of type "teardown". Its seq is the seq of the last event plus 1, its last_seq is the seq of the last event, and it links to the last event like any record.

5. Output
Print one verdict per input: PASS, FAIL or HOLD, and a short reason. Exit codes if your program uses them: 0 PASS, 1 FAIL, 2 HOLD, 3 no verdict (could not read, or your own error).

6. What this sheet leaves to you
What to do with an input that does not follow this sheet, how to treat a gap, an open stream, an empty file, a checkpoint that does not balance, a declared gap, a duplicate, and what makes a result FAIL rather than HOLD. Decide from the specification, and write each decision in CHOICES.txt.
